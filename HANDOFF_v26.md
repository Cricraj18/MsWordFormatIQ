## HOW TO WIRE watermark.ts INTO apply.ts (not done yet)
For every header part that apply writes from the TEMPLATE (word/header*.xml; template parts are copied untouched today): read the part text, call setWatermark(text, partName, {...options.watermark, seed: index + 1}) (index = position of the header part in sorted order, so shape ids differ per header), write the result instead of copying the part. Modes: "inherit" (default) leaves the template's own watermark as it is; "remove" removes it; "text" and "image" replace it. For "image": the picture bytes come from the user; for each header part: addImageRelationship(existing header rels text or undefined, "media/formatiq_watermark.<ext>"), pass the returned id as imageRelId, write the rels file at relsPathOf(headerPart), copy the picture ONCE to word/media/formatiq_watermark.<ext> (pick a free name with planPartNames), and make sure [Content_Types].xml has a Default for the extension (mergeContentTypes or add one). A template WITHOUT any header part cannot show a watermark: either create a header (needs a w:hdr part, a header relationship, a content-type Override and headerReference in every sectPr: this belongs to 5a) or report a warning "template has no header, watermark not added". "keepSource" cannot work while source headers are dropped (report a warning until keepSourceHeaders exists in 5a). Add counters to ApplyReport: watermarksRemoved, watermarksAdded.
Tests to add in apply.test.ts: template with a watermark header + each mode; template without header + "text" gives the warning; image mode adds rels, media and content type exactly once; validateDocx on the output has no errors.

## KNOWN LIMITS OF watermark.ts
- Only the first paragraph of a header is used; a header whose first paragraph is inside a table cell only is not special-cased (the first top-level paragraph is used).
- Watermarks that Word stores in other ways (DrawingML wps shapes inside mc:AlternateContent, shapes without the Word id) are not found.
- No size calculation from the real picture (the caller gives widthPt and heightPt) and no check of the picture bytes.
- Tried on hand-made header XML only.
